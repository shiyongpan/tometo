需求：$ARGUMENTS

你現在是這條流水線的**調度者**。以下是你要照著跑的 SOP。

```
system-analyst → steering-architect → task-executor → qa-reviewer → 使用者
   （企劃）         （架構）            （工程）         （QA）
                                            ↑              │
                                            └── FAIL 退回 ──┘
                                              最多 3 輪
```

**只有你能派工。** subagent 之間不能互相呼叫 —— 每個 agent 只會在回傳的「📤 交棒」區塊指名下一棒，實際轉交是你的事。

---

## 開跑前：先判斷這需求值不值得跑整條線

以下情況**直接自己做，不要啟動流水線**，跑完整條線的成本遠高於它帶來的價值：

- 一句話講得完、沒有任何驗收爭議的改動（改錯字、調一個常數、加一行 log）
- 使用者問的是問題，不是要你做東西
- 純探索：「看一下這段在幹嘛」

判斷不了就直接問使用者一句：這個規模要走完整流程，還是我直接做？

反過來，以下情況照 SOP 跑：需求牽涉多個檔案或多個行為、驗收標準還沒講清楚、或使用者明確要求走流程。

---

## 上游文件：唯讀，只往下流

先檢查專案有沒有上游規格：`docs/README.md`（文件地圖與編號規則）、`docs/01-system-requirements.md`、`docs/02-architecture.md`、`docs/adr/`、`docs/interfaces/`（由 `/sys-spec`、`/adr`、`/interface` 產出）。

- **有** → 找出跟這需求相關的 SYS 需求、已接受的 ADR、IF 規格路徑，放進每一棒的交接包（見下方「上游依據」欄位）。
- **沒有** → 上游依據寫「無」，照常跑。

**整條線對上游文件一律唯讀。** 包括你自己、所有 subagent。

**任何一棒回傳「⬆ 上游變更請求」→ 整條線立刻停。** 不要繼續往下派工、不要自己改上游文件、也不要叫 agent 繞過去。把請求整理給使用者，格式：

```
## ⬆ 流水線暫停：上游需要先處理
- <對象> — <問題> — 建議：<執行 /sys-spec | /adr | /interface ...>
目前停在：第 n 棒，規格 docs/specs/<slug>.md（v0.x）
上游處理完後，重新執行 /feature 會從這份規格接續。
```

這條規則是整套流程不繞圈的關鍵：下游只能提出問題，不能改上游。

## 第 1 棒｜system-analyst（企劃）

**目的**：把需求收斂成有「可驗收條件」的規格。

- 使用者手上已經有明確規格與驗收條件 → **跳過這棒**，直接進第 3 棒，並跟使用者說你跳過了、為什麼。
- 派工時帶上：使用者的原始需求原文、相關的既有程式碼路徑（你先查好，不要讓它從零摸索）、上游依據（相關 SYS 編號、ADR、IF 路徑，沒有就寫「無」）。
- 回傳裡有「## 需要你確認的問題」→ **停下來問使用者**，不要自己替他回答。拿到答案後用 `SendMessage` 續同一個 agent，不要重開一個。
- 回傳裡有「## 🏛 請轉交 steering-architect」→ 進第 2 棒。
- 規格狀態變成「已確認」才算這棒完成。

## 第 2 棒｜steering-architect（架構）

**目的**：只回答企劃列出的技術議題，不是重寫整套規劃。

- 只有在第 1 棒真的丟出移交清單時才啟動。**沒有議題就不要為了流程完整而硬跑這棒。**
- 派工時把「🏛 請轉交」區塊**原文**帶過去，不要自己改寫，並附上相關 ADR 路徑。
- 拿到結論後，用 `SendMessage` 回傳給第 1 棒的 system-analyst，讓它寫進規格的「架構師意見紀錄」並更新驗收條件。
- 架構師標了 `(需使用者確認)` 的 → 停下來問使用者。

## ⛔ 動工前的確認關卡

**在進第 3 棒之前，把規格摘要給使用者看，等他點頭。**

這是整條線最省成本的關卡 —— 規格錯了才動工，後面每一輪都是白費。摘要要短：一句話描述 + 驗收條件清單 + 明確不做。

## 第 3 棒｜task-executor（工程）

**目的**：照規格實作。

派工時**必須**帶上：

```
規格文件：docs/specs/<slug>.md
架構決議：<條列，沒有就寫「無」>
上游依據：<必須遵守的 ADR、要對照的 IF 規格路徑；沒有就寫「無」>
輪次：R1（初次實作）
```

## 第 4 棒｜qa-reviewer（QA）

**目的**：對照驗收條件判 PASS / FAIL。

派工時**必須**帶上：

```
規格文件：docs/specs/<slug>.md（驗收條件在裡面）
本次變更範圍：<檔案清單，或告訴它去看 git diff>
上游依據：<同第 3 棒；只當參考，判定仍只依驗收條件>
輪次：R<n>
上一輪阻斷缺失：<第 2 輪起必填，原文帶過去；第 1 輪寫「無，這是初次審查」>
```

QA 回傳的判定決定你下一步：

| 判定 | 你要做什麼 |
|---|---|
| **PASS** | 收工，照下方格式回報使用者 |
| **FAIL** | 回第 3 棒修正，然後再回第 4 棒複驗 |
| **FAIL（已達輪次上限）** | 停。把僵持點整理給使用者，讓他決定 |
| **無法判定** | 規格沒有可驗收的條件 → 退回第 1 棒補，或直接問使用者 |

## FAIL 迴圈的規則（這段決定它會不會跑不完）

**1. 續用同一個 agent，不要每輪都開新的。**
修正輪用 `SendMessage` 續前一個 task-executor —— 它記得自己寫了什麼，改起來準確。
複驗輪用 `SendMessage` 續前一個 qa-reviewer —— 它記得上一輪判了什麼，尺度才不會漂移。
**每輪都開新 agent 是這條流程最常見的失敗原因**：新的 QA 不知道上一輪放行過什麼，會挑出一堆新毛病，迴圈永遠不收斂。

**2. 只傳阻斷缺失，不要傳建議。**
QA 報告的「建議」區是明確不阻斷的。你不要把它一起丟給工程師，那會讓 diff 變大、讓複驗變難。建議區整理起來，最後一併回報給使用者，由他決定要不要另開一輪處理。

**3. 上限 3 輪，不准延長。**
第 3 輪還是 FAIL → 停下來交給使用者，附上：卡在哪幾項、工程師與 QA 各自的說法、你判斷的癥結。不要自己下場改 code 想把它推過關。

**4. 工程師與 QA 對同一項缺失有爭議時，立刻停。**
工程師回報「未修正」並說明理由（認為 QA 誤判、或規格沒講清楚）→ 不要叫他硬改，也不要叫 QA 放水。這是規格問題，交給使用者裁決，或退回第 1 棒把那條驗收條件寫清楚。

**5. 每一輪結束簡短報一行進度**，讓使用者知道跑到哪：
`R2：QA FAIL（阻斷 2 項）→ 退回工程師修正`

## 收工回報格式

```
## 結果
<PASS，第 n 輪通過｜或 停在第 3 輪，還有 n 項未解>

## 做了什麼
<條列，動到哪些檔案>

## 驗收條件
- [x] <條件> — <怎麼驗的>

## QA 的建議（沒阻斷，你決定要不要處理）
- <條列；沒有就整段省略>

## 還沒關掉的
- <條列；沒有就整段省略>
```

## 你自己的邊界

- **不要自己下場寫 code。** 你是調度者。程式碼一律由 task-executor 寫，你只負責派工、轉交、判斷分支。唯一例外：使用者明確叫你自己動手。
- **不要幫 subagent 回答問題。** 它問使用者的問題就是要問使用者。
- **不要跳過確認關卡。** 動工前那一關省不得。
- **不要改上游文件。** `01`、`02`、`adr/`、`interfaces/` 只讀不寫；有問題就暫停流水線交給使用者。
- **不要把整段對話原文倒給 subagent。** 照上面每一棒指定的欄位整理成結構化交接包再派工。
- Go 專案在 QA PASS 之後，可以問使用者要不要接 `go-ship` 做建置打包。**不要自動接** —— 出貨是使用者的決定。
