# ADR-0003：ES modules＋JSDoc 型別檢查，不建置、無外部套件

- 狀態：已接受
- 日期：2026-11-20
- 決策者：使用者（開發者）
- 對應需求：CON-001、002；QS-021、040；STK-020；ASM-002；ADR-0001

## 背景
`core/` 與 `data/` 要同時給瀏覽器與 Node（模擬工具、測試、之後的多人主機）使用（ADR-0001）。使用者熟悉北境求生的 classic script、不建置、無 npm。v0.1 開工前要決定程式怎麼組織與載入，不定的話第一批檔案會照舊寫成 classic script，之後要改就得補上每個檔案的 import 與 export。沒有期限。

決策驅動因素（使用者排定的順序）：
1. Node 能直接載入遊戲規則（QS-021、040）
2. 無相依、不建置（CON-001、002，STK-020）
3. 型別安全（可維護性）
4. 熟悉度（STK-020）

## 考慮過的選項
1. **A：ES modules，不建置**：瀏覽器原生 `import`，Node 直接載入同一批檔案。
2. **A+：ES modules＋JSDoc 型別檢查**：同 A，檔案開頭加 `// @ts-check`、型別寫在 JSDoc，由 VS Code 內建的 TypeScript 檢查，不安裝任何套件。
3. **B：classic script**（北境求生）：多個 script 共用全域範圍。
4. **C：TypeScript＋打包工具**（業界主流，例如 Vite、esbuild）：寫 TS，建置成 JS。

| 驅動因素 | A | A+ | B | C |
|---|---|---|---|---|
| 1 Node 直接載入 | ✅ | ✅ | ⚠️ 要用 `vm` 串檔執行 | ✅ |
| 2 無相依不建置 | ✅ | ✅ | ✅ | ❌ 違反 CON-001、002 |
| 3 型別 | ❌ | ⚠️ 只有編輯器檢查，CI 不檢查 | ❌ | ✅ |
| 4 熟悉 | ⚠️ | ⚠️ | ✅ | ❌ |

切換代價：
- A ↔ A+：隨時在檔案開頭加上或拿掉一行，幾乎沒有代價。
- A+ → C：JSDoc 型別可以轉成 TS，難度中等。
- B → A：每個檔案都要補上 import 與 export，難度中等。

## 決策
採用 A+：ES modules＋JSDoc `// @ts-check`，不建置、遊戲與工具都不用外部套件。

## 理由
- 前兩名驅動因素跟 A 一樣都符合；另外不花任何代價就能拿到編輯器的型別提示（第 3 名）。
- 使用者用 VS Code，內建 TypeScript 檢查，所以 A+ 有效。
- B 在第 1 名只部分符合；C 違反 CON-001、002。

## 後果
- 好處：沒有建置步驟與套件升級負擔；編輯器會提示型別錯誤。
- 代價：
  - 本機開發要用 HTTP 伺服器開（ES modules 不能用 `file://` 載入），用 Node 內建模組寫一支小伺服器（例如 `tools/serve.mjs`）。
  - 型別只在編輯器檢查，CI 不擋。
  - 不建置就沒有檔名雜湊：模組放在版本目錄，避免快取混用新舊模組（`02` R9）。
- 之後要注意：
  - 刻意不沿用北境求生的 classic script；保留的是「純 JS、無相依、不建置、Node 內建工具」（STK-020）。
  - 所有模組靜態 `import`，不用動態 `import()`（CON-003）。
  - 單檔備案（ASM-002）：公司擋掉 github.io 時，用 Node 內建工具把模組串成單一 HTML 檔，只限發佈用（CON-001 例外）。

## 重新檢視的條件
- 型別相關的錯誤（欄位拼錯、傳錯型別）在一個月內有 3 次以上沒被編輯器擋住、跑到測試或遊戲裡才發現：考慮在 CI 加型別檢查（要放寬 CON-002，或接受只在本機檢查）。
- 開始做多人版而且主機端程式超過 `core` 的大小：重新評估是否改用 C。
- 換用沒有內建 TypeScript 檢查的編輯器：A+ 的好處消失，等同 A。
